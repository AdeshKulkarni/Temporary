Here is why it disappeared:
Your system is actually built very securely! When the Final Approver clicked "Approve", the VoucherCommandService immediately completed the workflow. It cleared out the PENDING_AT (Next Stage) column because, as far as the workflow engine knew, there were no more stages left!
A fraction of a second later, the Oracle DB procedure ran and threw your intentional BadSqlGrammarException. Our code successfully caught the error and changed the status back to 'P' (Pending).
The Bug: Because the workflow engine already cleared out the PENDING_AT column, the system didn't know who the pending request belonged to! Therefore, it didn't show up in anyone's queue.
The Fix (Restoring the Workflow Stage):
We need to update our error handler so that when the database fails, it explicitly re-assigns the batch back to the final approver's exact workflow step.

    private void handleAsyncApprovalError(String batchId, String executorId, RequestStatus actionStatus, String defaultErrorMsg) {

        try {
            // CRITICAL FIX: The workflow engine advanced the stage BEFORE the DB procedure ran.
            // Because the DB procedure failed, we must manually REVERT the workflow stage 
            // back to the final approver so it reappears ONLY in their queue!
            
            // 1. Fetch the Final Step details for this specific workflow
            Map<String, Object> finalStepInfo = jdbcTemplate.queryForMap("""
                SELECT WORKFLOW_ID, WORKFLOW_ORDER FROM (
                    SELECT wt.WORKFLOW_ID, wt.WORKFLOW_ORDER
                    FROM WORKFLOW_TRANSITIONS wt
                    JOIN VOUCHER_POSTING vp ON wt.WORKFLOW_CODE = vp.APPROVAL_WORKFLOW
                    WHERE vp.BATCH_ID = ?
                    ORDER BY wt.WORKFLOW_ORDER DESC
                ) WHERE ROWNUM = 1
            """, batchId);
            
            String finalPendingAt = String.valueOf(finalStepInfo.get("WORKFLOW_ID"));
            Integer finalOrder = ((Number) finalStepInfo.get("WORKFLOW_ORDER")).intValue();

            // 2. Revert to Pending ('P') AND restore the PENDING_AT and CURRENT_ORDER columns
            jdbcTemplate.update("""
                UPDATE VOUCHER_POSTING 
                SET BATCH_STATUS = 'P', 
                    IS_EXECUTION_SCHEDULED = 'NO',
                    PENDING_AT = ?,
                    CURRENT_ORDER = ?
                WHERE BATCH_ID = ?
            """, finalPendingAt, finalOrder, batchId);

        } catch (Exception e) {
            log.error("Failed to revert workflow state for Batch: {}", batchId, e);
            // Safe fallback just in case the workflow transition fetch fails
            jdbcTemplate.update(
                "UPDATE VOUCHER_POSTING SET BATCH_STATUS = 'P', IS_EXECUTION_SCHEDULED = 'NO' WHERE BATCH_ID = ?",
                batchId
            );
        }

        // 3. The exact professional message requested
        String finalMsg = "Execution failed due to a database or server timeout. Please retry the approval process.";
        progressService.sendProgress(batchId, executorId, 0, "FAILED", finalMsg);

        String vid = null;
        String creatorId = null;

        try {
            Map<String, Object> batchInfo = jdbcTemplate.queryForMap(
                    "SELECT VID_FK, CREATED_BY FROM VOUCHER_POSTING WHERE BATCH_ID = ?", batchId
            );
            vid = (String) batchInfo.get("VID_FK");
            creatorId = (String) batchInfo.get("CREATED_BY");
        } catch (org.springframework.dao.EmptyResultDataAccessException e) {
            log.warn("Batch info not found for Batch: {}", batchId);
        }

        // 4. Log the "Execution Failed" event in Workflow History so the Frontend knows to show the Retry button
        workflowEngine.logWorkflowAction(batchId, vid, "Execution Failed", executorId, finalMsg, null);

        // 5. Send the notification explicitly telling the user to retry
        try {
            String checkerMsg = String.format("Execution alert for Batch '%s': %s", batchId, finalMsg);
            notificationWriterService.createNotification(executorId, null, checkerMsg, "/voucher-view/" + batchId, batchId, "VoucherService");

            if (creatorId != null && !creatorId.equalsIgnoreCase(executorId)) {
                String makerMsg = String.format("Execution alert for your Batch '%s': %s", batchId, finalMsg);
                notificationWriterService.createNotification(creatorId, null, makerMsg, "/voucher-view/" + batchId, batchId, "VoucherService");
            }
        } catch (Exception e) {
            log.warn("NOTIFICATION_WARN | Batch: {} | Could not send failure notifications", batchId);
        }
    }

Why this fixes the issue perfectly:
By running that quick SELECT query in step 1, the code automatically looks up the exact Workflow Stage ID that the final approver belongs to.
In step 2, it forces the VOUCHER_POSTING table to reset its PENDING_AT column right back to that specific stage.
Now, when you refresh your authorization page, the database will successfully see that the batch is pending specifically at the Final Approver's stage, and it will instantly show up in their queue with the orange "Retry Approval" button waiting for them!
