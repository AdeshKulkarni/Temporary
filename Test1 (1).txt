CommonRequestService Backend Architecture Guide : 
1. Overview
This document outlines the architecture of the backend system, which is composed of several microservices. The primary focus here is the CommonRequestService and the MasterDataService.
2. CommonRequestService
This service's bounded context is the Change Management Workflow. It handles the creation, validation, processing, and auditing of all change requests.
Key Architectural Concepts
2.1. Fail-Fast Payload Validation
When a request is created via POST /create-request, the system uses Jackson's polymorphic deserialization (@JsonTypeInfo) to intelligently validate the payload object.
●	The CreateRequestDto uses the requestType field to determine which specific DTO (SegmentPayloadDto, CglPayloadDto) to map the payload to.
●	Spring's validation (@Valid) is triggered automatically, catching any structural or data-related errors before the service layer is invoked. This provides immediate feedback to the Maker(Creator).
2.2. Pre-emptive Uniqueness Check
Before creating a new request, the RequestService performs two critical pre-flight checks:
1.	It extracts the primary key from the payload (e.g., segmentCode or a computed cglNumber) and sets it as the targetId on the CommonReq entity.
2.	It queries the database to ensure no other PENDING or ACCEPTED request for the same targetId already exists. This prevents duplicate conflicting requests.
2.3. Strategy Pattern for Approvals
The logic for approving a request is handled by the Strategy Pattern to keep the core service clean and extensible.
●	The approve method in the RequestTypeStrategy interface is now smarter. It checks the request's changeType and branches its logic for ADD vs. UPDATE operations, including uniqueness checks and fetching existing records by targetId.
2.4. API Response Handling
The system uses a @JsonRawValue annotation on the getPayload() method of the CommonReq entity. This is a targeted fix to ensure that the JSON string stored in the database is correctly rendered as a nested JSON object in the final API response, preventing double-serialization issues.
3. Security
3.1 Current Implementation
●	Authentication: Services expect a JWT Bearer token in the Authorization header.
●	User ID Extraction: The userId is currently extracted using a local JwtUtil class. This utility performs a basic decode and does not validate the token's signature.
3.2 TODO: Future Security Enhancements (CRITICAL)
The current security implementation is for development and testing only. The following enhancements are required before moving to production:
●	[ ] Create a Shared security-jwt-lib: A common library must be created to handle all JWT validation. This library will contain the production-ready logic to:
○	Perform full signature validation against the identity provider's issuer-uri.
○	Securely extract user information from the validated token.
○	Contain the custom JwtRoleConverter to map numeric roles (51, 52) to Spring Security authorities.
●	[ ] Implement Method-Level Security: Once the shared library is in place, the service methods in CommonRequestService must be annotated with @PreAuthorize to enforce role-based access control (e.g., @PreAuthorize("hasAuthority('ROLE_MAKER')")). This will replace the temporary, insecure JwtUtil.
