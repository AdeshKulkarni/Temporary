This is the exact roadblock every engineer hits when first implementing the Strategy pattern in a real system. You have a single interface (like Rules), but CourseCapacity only cares about the Course, MeetPrerequisites cares about the Student, and coursesRestricted might need both.
Because Java requires interface method signatures to match exactly, you cannot have one rule take (Student s) and another take (Course c) if they are going to live in the same List<Rules>.
Here are the two industry-standard ways to solve this for Low-Level Design interviews.
Approach 1: The Context/Request Object (Best Practice)
Instead of passing individual entities, you create a wrapper class that holds all the context for the current transaction. This is how enterprise systems pass data through validation engines.
1. Create the Request Object:
public class RegistrationRequest {
    private Student student;
    private Cource cource;

    public RegistrationRequest(Student student, Cource cource) {
        this.student = student;
        this.cource = cource;
    }
    
    public Student getStudent() { return student; }
    public Cource getCource() { return cource; }
}

2. Unify Your Interface:
Drop CourceLeval and StudentLeval. Make every single rule implement one unified interface.
public interface Rules {
    boolean check(RegistrationRequest request); // Or return a Result object
}

3. Implement the Rules:
Now, each rule just pulls what it needs from the wrapper object and ignores the rest.
public class CourceCapacity implements Rules {
    @Override
    public boolean check(RegistrationRequest request) {
        Cource c = request.getCource();
        // The rule only uses the course, ignoring the student
        return UniversityDataRegistry.getCurrentCap().getOrDefault(c.getCourceId(), 0) < c.getCapacity();
    }
}

public class MeetPrerequisites implements Rules {
    @Override
    public boolean check(RegistrationRequest request) {
        Student s = request.getStudent();
        Cource c = request.getCource();
        // This rule uses both to verify the student has the course's prerequisites
        return s.getCourceComplated().containsAll(c.getPrerequisites());
    }
}

Approach 2: Multi-Parameter Signature (The Quick Fix)
If you are rushing in a 90-minute interview and don't want to create a wrapper class, just pass both objects directly into the interface method.
public interface Rules {
    boolean check(Student student, Cource cource);
}

If CourceCapacity only needs the course, it simply ignores the student parameter inside its implementation.

By using a RegistrationRequest object, you guarantee that if the university later adds a rule requiring the current timestamp or the student's payment status, you just add that field to the RegistrationRequest class without having to rewrite the method signatures of your existing rules.
