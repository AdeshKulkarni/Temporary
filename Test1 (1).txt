I completely understand the frustration. Dealing with enterprise security scanners like JFrog Xray can feel like playing an endless game of whack-a-mole.
Here is exactly what is happening: The compilation error from the previous step is completely fixed. However, because you are importing massive big-data frameworks like Hadoop and Hive, they act like Trojan horses, secretly pulling in dozens of outdated libraries behind the scenes.
If you look at the AFFECTED COMPONENT column in your log, you can see the main culprits:
 * htrace-core: This Hadoop tracing library is pulling in jackson-databind:2.4.0 from 2014, which is single-handedly responsible for almost all of those 💀Critical violations.
 * netty: Spring Boot 4.1 uses Netty 4.2.15.Final, but JFrog just flagged that as vulnerable and wants 4.2.16.Final.
 * zookeeper: JFrog is rejecting 3.9.1 and demanding 3.9.5.
To silence JFrog, we need to add a comprehensive <dependencyManagement> block that forces your application to use the exact versions listed in JFrog's FIXED VERSIONS column.
Step 1: Update your <dependencyManagement>
Replace your current <dependencyManagement> block in your pom.xml with this expanded version. This uses "BOMs" (Bill of Materials) to force Jackson and Netty to secure versions all at once, and updates the rest of the stragglers JFrog found:
    <dependencyManagement>
        <dependencies>
            <!-- 1. Force Modern Jackson (Fixes the massive list of htrace-core Jackson 2.4.0 Criticals) -->
            <dependency>
                <groupId>com.fasterxml.jackson</groupId>
                <artifactId>jackson-bom</artifactId>
                <version>2.21.4</version>
                <type>pom</type>
                <scope>import</scope>
            </dependency>

            <!-- 2. Force Secure Netty 4.2.x (Fixes all the High/Critical Netty 4.2.15 issues) -->
            <dependency>
                <groupId>io.netty</groupId>
                <artifactId>netty-bom</artifactId>
                <version>4.2.16.Final</version>
                <type>pom</type>
                <scope>import</scope>
            </dependency>

            <!-- 3. Zookeeper (Fixes CVE-2026-24281) -->
            <dependency>
                <groupId>org.apache.zookeeper</groupId>
                <artifactId>zookeeper</artifactId>
                <version>3.9.5</version>
            </dependency>

            <!-- 4. Thrift (Fixes CVE-2026-43869) -->
            <dependency>
                <groupId>org.apache.thrift</groupId>

Step 2: Handle the un-fixable xercesImpl
If you look closely at the JFrog log for apache-xerces:xercesImpl, the FIXED VERSIONS column is completely blank. This means there is no secure version available.
Because modern Java has built-in XML parsing, we can just delete it entirely. Go down to your <dependencies> block, find your hadoop-common dependency, and add this to its <exclusions> list alongside the others:
                <!-- Remove vulnerable xerces entirely -->
                <exclusion>
                    <groupId>xerces</groupId>
                    <artifactId>xercesImpl</artifactId>
                </exclusion>

Add these changes, and this should wipe out that entire table of JFrog errors.
