# Dependency Injection: Constructor vs. Field Injection

## 1. Field Injection (`@Autowired` on properties)
* **Initialization Order:** The object instance is created *first*, and dependencies are injected *later* via Java Reflection.
* **The `final` Keyword Restriction:** You cannot use `final`. Because the dependency is not provided at the exact moment of object creation, Java prohibits locking the variable.
* **State Risk:** Creates a temporary state where the object exists but its dependencies are `null`. This requires starting the heavy Spring context just to write a simple unit test.

## 2. Constructor Injection (Recommended)
* **Initialization Order:** Dependencies must be fully resolved by the Spring container *before* the object can even be instantiated. 
* **The `final` Keyword Advantage:** Supported and encouraged. Dependencies are injected directly through the constructor, meaning they can be locked as `final` forever.
* **Guaranteed Safety:** It is impossible to instantiate the object in an uninitialized state. The Java compiler enforces that all dependencies are present.

## 3. Circular Dependencies (Class A ↔ Class B)
* **With Field Injection:** Hides the architectural flaw. The application context will often start successfully, only to crash unexpectedly at runtime when the circular loop is invoked.
* **With Constructor Injection:** Fails fast and loudly. Spring cannot resolve which bean to build first, resulting in an immediate startup error that forces the developer to fix the bad design.
