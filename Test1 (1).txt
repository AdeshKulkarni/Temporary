Seeing a massive wall of 💀Critical and 🔥High security violations from your company's code scanner can definitely be overwhelming, but this is a very standard part of maintaining enterprise Java applications.
Looking at your scan report, the vast majority of these vulnerabilities are transitive dependencies—meaning you didn't explicitly add these vulnerable libraries to your project. Instead, you added a framework (like Hadoop, HBase, or Zookeeper), and that framework pulled in outdated, vulnerable versions of underlying libraries like Netty, Jackson, and Guava.
Here is the step-by-step guide on how to clear these violations and fix your project.
Step 1: Track Down the Culprits
Before you can fix a transitive dependency, you need to know which direct dependency is bringing it into your project. Open your terminal, navigate to your project directory, and run this Maven command:
mvn dependency:tree

This will output a tree structure. Search the output for libraries like jackson-databind:2.4.0 or netty-all:4.1.12.Final. The tree will show you exactly which top-level library is responsible for pulling them in.
Step 2: Force Secure Versions using <dependencyManagement>
The cleanest and most effective way to fix transitive CVEs is to use Maven's <dependencyManagement> block. This forces your entire project (and all underlying frameworks) to use the secure version of a library, overriding whatever the older frameworks request.
Based on your scan report, you need to force updates for Netty, Jackson, Tomcat, Guava, and Zookeeper. Add the following block to your pom.xml (right above your <dependencies> block):
<dependencyManagement>
    <dependencies>
        <!-- Fix Tomcat Embed Core (CVE-2026-55276) -->
        <dependency>
            <groupId>org.apache.tomcat.embed</groupId>
            <artifactId>tomcat-embed-core</artifactId>
            <version>11.0.23</version>
        </dependency>

        <!-- Fix Netty framework vulnerabilities (CVE-2019-20444, etc.) -->
        <dependency>
            <groupId>io.netty</groupId>
            <artifactId>netty-all</artifactId>
            <version>4.1.136.Final</version>
        </dependency>
        <dependency>
            <groupId>io.netty</groupId>
            <artifactId>netty-handler</artifactId>
            <version>4.1.136.Final</version>
        </dependency>
        <dependency>
            <groupId>io.netty</groupId>
            <artifactId>netty-codec</artifactId>
            <version>4.1.136.Final</version>
        </dependency>

        <!-- Fix Modern Jackson vulnerabilities (CVE-2020-9548, etc.) -->
        <dependency>
            <groupId>com.fasterxml.jackson.core</groupId>
            <artifactId>jackson-databind</artifactId>
            <version>2.15.0</version> <!-- Or whatever the latest approved 2.x version your company allows -->
        </dependency>
        <dependency>
            <groupId>com.fasterxml.jackson.core</groupId>
            <artifactId>jackson-core</artifactId>
            <version>2.15.0</version>
        </dependency>

        <!-- Fix Guava (CVE-2023-2976) -->
        <dependency>
            <groupId>com.google.guava</groupId>
            <artifactId>guava</artifactId>
            <version>32.0.1-jre</version>
        </dependency>

        <!-- Fix Protobuf (CVE-2024-7254) -->
        <dependency>
            <groupId>com.google.protobuf</groupId>
            <artifactId>protobuf-java</artifactId>
            <version>3.25.5</version>
        </dependency>
        
        <!-- Fix Zookeeper (CVE-2023-44981) -->
        <dependency>
            <groupId>org.apache.zookeeper</groupId>
            <artifactId>zookeeper</artifactId>
            <version>3.9.1</version>
        </dependency>
    </dependencies>
</dependencyManagement>

Step 3: Handle Legacy "End-of-Life" Packages (Exclusions)
Your scan shows severe vulnerabilities in org.codehaus.jackson:jackson-mapper-asl:1.9.2. This is the ancient, deprecated "Jackson 1.x" library. Modern applications use com.fasterxml.jackson (Jackson 2.x).
Because org.codehaus.jackson is dead, there are no modern secure versions (unless you are using proprietary Cloudera patched distributions). The best approach is to completely exclude it from the dependencies that are pulling it in (like htrace-core or Hadoop).
Find the dependency pulling it in (using the dependency:tree command from Step 1), and update your pom.xml like this:
<dependency>
    <groupId>org.apache.htrace</groupId>
    <artifactId>htrace-core</artifactId>
    <version>3.2.0-incubating</version>
    <exclusions>
        <!-- Surgically remove the highly vulnerable legacy Jackson -->
        <exclusion>
            <groupId>org.codehaus.jackson</groupId>
            <artifactId>jackson-mapper-asl</artifactId>
        </exclusion>
        <exclusion>
            <groupId>org.codehaus.jackson</groupId>
            <artifactId>jackson-core-asl</artifactId>
        </exclusion>
    </exclusions>
</dependency>

Step 4: Verify and Re-Scan
Once you have added the <dependencyManagement> block and the necessary <exclusions>, you need to verify that your changes took effect.
 * Clean and compile the project: Run mvn clean install to ensure that forcing these newer versions didn't break any Java code (sometimes major version jumps in libraries like Guava or Netty can introduce breaking code changes).
 * Check the tree again: Run mvn dependency:tree and verify that jackson-databind:2.4.0 has been replaced by your newer version.
 * Re-run the scanner: Push your code or run your local security scanner again. The report should now be clear of these specific CVEs.
