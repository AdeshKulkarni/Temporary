Your IDE is very smart! It is highlighting those new methods as "not in use" because we added them to ValidationStateManager, but we haven't yet updated your VoucherAsyncWorker to actually call them.
Right now, your VoucherAsyncWorker.java is still using the old method (getValidRowsFromCache) that causes the memory crash.
Here is exactly how to connect the new methods and fix the "not in use" warning.
### Step-by-Step Fix
 1. Open your **VoucherAsyncWorker.java** file.
 2. Find the method named **executeAsyncBatchCreation**.
 3. Inside that method, **delete everything** starting from List<ExcelRowData> cachedRows = ... all the way down to CompletableFuture.allOf....
 4. **Paste this new logic** in its place:
```java
            // --- NEW: TRUE STREAMING LOGIC ---
            progressService.sendProgress(batchId, creatorId, 5, "PROCESSING", "Preparing Data...");

            // 1. Ask Redis how many chunks exist (Does NOT load data into memory)
            int totalChunks = validationStateManager.getTotalChunks(requestId);
            
            if (totalChunks == 0) {
                log.error("CACHE_MISS | Batch: {} | Status: No valid rows found", batchId);
                progressService.sendProgress(batchId, creatorId, 0, "FAILED", "Data cache expired or empty.");
                return;
            }

            int batchSize = 5000; 
            long totalRows = batchSize * (long) totalChunks; // Used for progress bar estimation
            
            List<CompletableFuture<Void>> futures = new ArrayList<>();
            AtomicReference<BigDecimal> totalDebit = new AtomicReference<>(BigDecimal.ZERO);
            AtomicReference<BigDecimal> totalCredit = new AtomicReference<>(BigDecimal.ZERO);
            AtomicInteger completedChunks = new AtomicInteger(0);

            // 2. PARALLEL CHUNKING - Fetch exactly ONE chunk at a time inside the background thread
            for (int i = 0; i < totalChunks; i++) {
                final int chunkIndex = i;
                final int startIdx = i * batchSize;

                CompletableFuture<Void> future = CompletableFuture.supplyAsync(() -> {
                    // -> THIS MAKES THE METHOD "IN USE" <-
                    // The background thread fetches just its own 5000 rows, then garbage collects them
                    return validationStateManager.getChunkFromCache(requestId, chunkIndex);
                }, chunkWorkerExecutor).thenAcceptAsync(chunk -> {
                    if (contextMap != null) MDC.setContextMap(contextMap);
                    try {
                        self.processChunkRaw(chunk, batchId, journalPrefix, commonRemarks, creatorId, creatorRole, startIdx, totalDebit, totalCredit);
                        successfulRowsCount.addAndGet(chunk.size());
                    } finally {
                        MDC.clear();
                    }
                }, chunkWorkerExecutor).thenRun(() -> {
                    int done = completedChunks.incrementAndGet();
                    int percent = 5 + (done * 90 / totalChunks);
                    progressService.sendProgress(batchId, creatorId, percent, "PROCESSING", String.format("Writing chunks: %d of %d", done, totalChunks));
                });
                
                futures.add(future);
            }

            // Wait for all 50 threads to finish processing their individual chunks
            CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).get(45, TimeUnit.MINUTES);
            // --- END NEW STREAMING LOGIC ---

```
### Why this fixes the problem:
By making this change, the old getValidRowsFromCache method will now be the one that shows as "not in use" (and you can safely delete it from ValidationStateManager).
Instead of the main thread trying to hold 500,000 rows in memory, your application will now spin up background threads that each call getChunkFromCache(requestId, chunkIndex). They process their 5,000 rows, write them to the database, and immediately throw the data away, completely eliminating the Out of Memory crash!
