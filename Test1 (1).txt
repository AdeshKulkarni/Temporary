1.1 Purpose of this Document 

This comprehensive user manual serves as the primary instructional guide for operating the Voucher Posting & Authorization. It is purposefully designed to assist all designated stakeholders—including Makers, Checkers, Approvers Administrators across various teams (such as SBI GLIF, TCS GLIF, and TCS IMPL etc)—in navigating the application accurately and efficiently. The document outlines the end-to-end processes required for Voucher IDs (VIDs), initiating manual or bulk postings, and executing multi-tiered authorization workflows. By providing clear, step-by-step instructions alongside strict business rules.  

Whether you are submitting a new financial batch, auditing a pending request, or tracking a voucher's entire lifecycle, this guide will help out 

 

 

1.2 System Overview & Key Features 

The Voucher Posting & Authorization System is a secure, role-based financial application built to manage, validate the vouchers. It minimizes human error through strict system-level validations and ensures Valid data to posting using the multistage approval system 

Key Features Include: 

Maker-Checker : user can be both create and approve a financial entry, depending upon the flow of that voucher guaranteeing a secure separation of duties. 
 

Voucher IDs (VIDs): Utilizes VID  (created by SBI GLIF) that act as templates, ensuring Makers only post transactions to approved categories. 
 

Dual Entry Methods: Supports Manual Data Entry and robust Bulk Excel Uploads for processing thousands of rows simultaneously. 
 

Real-Time Validation: The system actively intercepts errors by forcing exact Debit and Credit balancing across all Branch and Currency combinations before a batch can even be submitted. 
 

Flexible Execution Scheduling: Allows Creator or Final Approvers to post vouchers immediately or schedule them to automatically execute at a specific time later in the day. 
 

Comprehensive Audit Trails: Features a detailed "View & Action" that tracks every stage, action, timestamp, and user remark throughout the voucher's lifespan.

2. Getting Started 

2.1 System Access 

Access to the Voucher Posting & Authorization System is strictly governed by Role-Based Access Control (RBAC).  

A. Roles: TCS GLIF & SBI GLIF These roles act primarily as the "Makers" (and intermediate Checkers) of the financial pipeline. 

Voucher Posting: Initiate new batches using assigned VIDs (Supports both Manual Entry and Bulk Excel Upload). 

Voucher Posting Status: Track the lifecycle, workflow progress, and audit history of submitted batches. 

Voucher Authorization: Review, approve, or reject pending batches submitted by other makers. 

Search Category-Wise Voucher: Query and view vouchers categorized by specific business units. 

Search CGL / Branch / Asset & Liabilities: Access inquiry screens to safely search and validate General Ledgers, Branch Codes, and Asset/Liability configurations. 

B. Role: SBI GLIF This role acts as the "checkers" and "Final Approver" of the System 

Request Voucher: Create and configure the Voucher IDs (VIDs), defining descriptions and issue categories. 

View Request Voucher: Audit and manage existing VID configurations. 

Voucher Authorization: Perform the final approval on batches and dictate the final Execution Time (Immediate or Scheduled). 

Search Category-Wise Voucher: Query and view vouchers categorized by specific business units. 

Search CGL / Branch / Asset & Liabilities: Access inquiry screens to safely search and validate General Ledgers, Branch Codes, and Asset/Liability configurations. 

 

2.2 Important Business Rules & Constraints 

To maintain the highest level of financial data integrity, the system hard codes several non-by passable constraints. Please keep the following rules in mind while using the system: 

Balancing Rule: For every batch submitted, the Total Debits must perfectly equal the Total Credits. The system enforces this balance at a granular level: it must balance per Branch and per Currency. 

Self-Approval Block (Segregation of Duties): A user is physically restricted from authorizing (Approving or Rejecting) any batch that they created. If a Maker navigates to the Authorization screen, the "Proceed to Action" button for their own batches will be disabled with a security violation warning. 

Amount Limitations: Financial amounts cannot be zero. Input fields enforce a strict limit of up to 16 integer digits and exactly 4 decimal places. 

Remarks Constraints: Action remarks and row-level remarks are strictly mandatory. They must be between 2 and 30 characters long. To prevent data corruption, the system only accepts alphanumeric characters, single space between the words. 

 

3 Voucher ID (VID) Creation 

 
 
3.1 Understanding the Role of VID 

What it is: The VID (Voucher ID) acts as a mandatory authorization ticket that must be generated before any actual voucher entries can be posted into the system. It is uniquely generated in the format VID-YYMM-XXXXX.  

Why we use it: Instead of users blindly posting vouchers, the VID ensures every posting is tied to a specific, pre-approved request. It also gives lifecycle control—allowing them to view all active requests, track which vouchers were posted against them, and dynamically terminate or close a VID to instantly prevent any further unauthorized postings. 

3.2 Creating a New VID 

What it is: The execution step where the user submits the structured form to generate the unique identifier. Alongside internal data, it can capture an optional SD Request Number (a numeric, comma-separated reference to an external SCORE request).  

Why we use it: This step transitions the requirement from a draft into a live, actionable entity in the database. Upon clicking "Create," the system validates the inputs, provisions the unique VID-YYMM-XXXXX identifier, and displays the summary on-screen. Linking the external SD request numbers during creation ensures cross-system tracking between Fin Core and the SCORE system. 

 

3.3 Defining Voucher Category  

Select a voucher category to initiate the voucher request. To define a custom category, choose the 'Other' option. (at last) This allows you to establish specific validation rules, detailing permitted and restricted parameters, which are displayed below the text field. 

 

 

 

3.3 Defining Issue Category  
 

 

Refining Issues (Granular Classification): A multi-select tool where users pinpoint the exact systemic or operational issues triggering the voucher. It includes an "Add Issue" fail-safe if the specific problem isn't listed. 

3.4 Description, Allowed Target Roles 

What it is: The context and security layer of the VID creation process. 

Description: A mandatory text field (up to 500 characters) where the user must provide the detailed analysis or justification for the voucher posting. 
 

Allowed Target Roles: A mandatory dropdown where the creator defines the specific "Allowed Role." So that only allowed roles can post the voucher 
 
 
 

 

 

 

4: Voucher Posting / Batch Creation 

(Roles: TCS GLIF, TCS IMPL) 

Once a Voucher ID (VID) is successfully generated and active, authorized users can begin drafting the actual financial entries against it. This module governs how data is entered, validated, and scheduled for execution. 

4.1 Accessing Assigned VIDs 

 

To initiate a voucher posting, the user must first select an active VID from their queue. 

The Rule: The system strictly enforces a 1:1 relationship—only one voucher batch can be created against a single VID at a time. 

Reusability: If a submitted voucher batch is rejected/delete during the process of workflow, the system releases the lock, allowing the user to reuse that same VID to create and submit a corrected batch. 

 

 

 

 

 

 

 

4.2 Selecting the Entry Method (Manual vs. Bulk) 

 

 

Depending on the volume of the transactions, users are presented with two distinct pathways in the Voucher Posting Module: 

Manual Entry: Best for low-volume adjustments where users can input data row-by-row directly into the manual posting row by row 
 

Bulk Excel Upload: Designed for high-volume, mass voucher creations, allowing users to process thousands of entries via a standardized Excel. 

 

 
 

 

4.3 Manual Voucher Entry 

The manual entry screen acts as an interactive grid, it will validate all validation as the user click on the validate button.  
 

 

4.3.1 Common Batch Remarks 

Users have the flexibility to define the narrative of the transaction. They can either apply a Common Remark that cascades across the entire batch (saving time) or input unique, separate remarks for each individual voucher row. To ensure database safety, remarks are strictly restricted to alphanumeric characters. 

4.3.2 Entering Transaction Rows 

For each row, the user must define the financial transaction parameters: 

Branch & CGL (Mandatory): As the user inputs the Branch code and CGL (General Ledger) code, the system performs a live database search. Only valid, active codes existing in the database can be selected. 

Currency (Mandatory): Selected from a predefined dropdown. 

Amount (Mandatory): The system enforces strict numerical formatting (up to 9999999999999999.9999). Negative values are strictly blocked corrections must be handled via opposite debit/credit entries. 

Type (Mandatory): The user designates the row as either a Debit or Credit. 

Product Code (Optional): A numeric identifier (up to 8 digits) for further classification. 

4.3.3 Grid Controls (Add, Delete, Reset) 

The interface provides standard grid controls allowing users to easily construct their batch. Users can click Add Row to append new transaction lines or use Delete Row to remove incorrect entries before submission. or reset to clear all data from the input fields before submission. 

 4.3.4 Validation & Submission 

Upon clicking Validate, the system does not simply save the data; it runs the entire batch through a rigorous set of business logic validations (e.g., ensuring Debits equal Credits, verifying branch validity). The batch will only successfully submit to the next phase if 100% of the internal validations pass. 
 

 

4.4 Bulk Excel Upload 

For massive financial postings, the UI provides a Bulk Upload facility. 
 

 

4.4.1 Downloading the Template 

Users initiate the process by downloading a standardized Excel template directly from the upload screen. This ensures the user is working with the latest template required by the voucher bulk upload 

 

 

4.4.2 Formatting Rules & Data Entry 

The downloaded template enforces a strict, predefined column order: Branch, Currency, CGL, Amount, Type, Remarks, Product Code. 

Mandatory fields are clearly marked with an asterisk (*). 

The Rule: The column order is locked and must be maintained exactly as-is. Users fill this sheet out offline, leveraging standard Excel features to manage large datasets. 

4.4.3 Uploading and System Validation 

 

 

Once the Excel file is prepared, the user uploads it via the UI. The system parses the file and applies the same rigorous business validations used for manual grid entries. If validation fails at any stage, the system generates a detailed Error Report Excel File.  This report pinpoints the exact row and nature of the error, enabling the user to correct the data and re-upload efficiently.  

The validation process occurs in three sequential stages:  

Format Validation:  This stage checks for syntactic correctness and adherence to data types. It identifies issues such as invalid currency formats, dates entered as text, or remarks exceeding the maximum character limit.  

Database Validation: (Referential Integrity) This stage verifies that the data entered exists within the system's master records. It flags errors where referenced entities—such as CGL, Branch codes, or Currency — do not exist in the System.  

Debit/Credit Validation: The final stage ensures accounting integrity by verifying that debits equal credits for the specific entry or batch. Any mismatch triggers a balancing error. 

5. Execution Configuration: (Common final Stage for the Manual & Bulk Upload) 

This is the final stage of the batch/manual creation process. Once the transaction data has successfully passed all format, database, and debit/credit validations, the creator must define the execution timing. The system offers two distinct modes Immediate & Scheduled   
 
 

 
Immediate Execution: Select this option when the adjustment needs to be reflected in the system instantly, subject to necessary approvals. Upon approval, the batch processes immediately without delay.  
 

Scheduled Execution: Ideal for planned downtime or end-of-day reconciliations, this option allows the user to configure a specific execution time. Scheduling Rule: The system permits scheduling from 30 minutes in the future up to 23:59 on the current day. Benefit: This constraint ensures that batches are staged securely without impacting active daytime operational loads, allowing for controlled processing during off-peak hours. 

 

5. Module 3: Voucher Authorization Workflow 

5.1 The Workflow Explained (e.g., Maker -> Checker -> Approver) 

5.1 The Workflow Explained The voucher posting process requires multiple Checkers. First, a "Maker" creates and submits a voucher batch. Then, it goes to next "checker" to review and approve Finally, an "Approver" gives the final approval, and the system executes the transaction.  

 

5.2 Reviewing Pending Requests Go to the "Voucher Authorization" screen from the main menu. Here, you will see a table listing all the voucher batches that are currently waiting for your approval. You will only see batches assigned to your role. 

 

5.3 Using the "View & Action" Button To see more information about a pending request, click the "View & Action" button next to it in the table. This opens a detailed screen.  

 

5.3.1 Reviewing Batch and Voucher Details:  
 
At the top of the screen, you can check the Voucher ID (VID), description, category, creator name, total number of entries, and the date it was created. 

5.3.2 Downloading the Data Extract:  
 
If you want to check the exact voucher entries, click the "Download Batch" button. This will download an Excel file containing all the data rows for that batch. 

5.3.3 Tracking Workflow Progress & History:  
 
Scroll down to see the visual timeline. It shows which stages are completed, pending, or rejected. Below that, the "Workflow History" section shows exactly who acted, at what time, and what remarks they left. 

 

 

 

5.4 Executing an Authorization Decision  

Once you have checked the details, click the "Proceed to Action" button at the bottom of the screen to make your decision. 

 5.4.1 Approving a Request:  
 
Click the green "Approve Request" option to move the batch forward to the next stage. 

5.4.2 Rejecting a Request:  
 
Click the red "Reject Request" option if you want to reject the batch. This will terminate the workflow. 

5.4.3 Providing Action Remarks:  
 
Before you click Submit, you must type a reason in the "Action Remarks" box. Remarks must be between 2 and 30 characters long and can only contain Alphanumeric and Single space after each word 

 

5.5 Final Approver Privileges & Schedule Overrides  
 
If you are the final approver, you have special scheduling options before you submit. You can select "Keep Original Routing" to run the batch at the exact time chosen by the Maker. Or you can select "Override Schedule" to pick a brand-new execution time for today.  

 

 

 

6. Module 4: Voucher Posting Status & Tracking 

6.1 Searching and Filtering Batches  
 
Go to the "Voucher Posting Status" screen. You can quickly find any batch by typing the Batch ID or the VID into the search boxes at the top of the table columns. 

 

6.2 Understanding Batch Status The progress column shows the status of your batch 

Pending: The batch is currently waiting for someone to approve it. 

Completed / Posted: The batch was fully approved and successfully executed by the system. 

Rejected: The batch was denied by an approver and stopped. 

Escalated: The batch has been waiting at an approval stage for too long without action. 

Execution Failed: The system tried to process the batch but encountered a server error. (The Production Support Team is automatically notified to retry it). 

6.3 Cancelling a Draft/Submitted Batch (Maker Only)  

If you are the Maker who created the batch, you can delete it only if it is still at the very first pending stage. Click "View & Action" on your batch, scroll to the very bottom, and click the red "Cancel Voucher Batch" button to permanently delete it.
