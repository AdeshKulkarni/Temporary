# Spring AOP Proxies: JDK vs. CGLIB

Spring uses proxies (wrapper classes) to magically inject behaviors like `@Transactional`, `@Async`, or `@Configuration` caching without altering your actual code. Spring automatically chooses between two types of proxies:

| Feature | JDK Dynamic Proxy | CGLIB Proxy |
| :--- | :--- | :--- |
| **Source** | Native Java feature | Third-party library (built into Spring) |
| **Trigger Condition** | The target class **implements an Interface** | The target class has **NO Interface** |
| **How it Works** | Generates a fake class that implements the *same interface* | Generates a **Subclass** that `extends` your class and overrides methods |
| **Spring Examples** | `@Service` or `@Repository` that implements an interface | `@Configuration` classes, or beans with no interfaces |
| **Strict Limitations**| Can only proxy methods defined in the interface | Cannot proxy `final` classes, `final` methods, or `private` methods |

> **Key Rule of Thumb:** If it has an interface, Spring defaults to JDK. If it doesn't, Spring falls back to CGLIB. (Note: Spring Boot actually forces CGLIB by default for everything now unless configured otherwise, to prevent interface casting errors).
